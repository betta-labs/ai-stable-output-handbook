# P2 试点证据包总览

本目录将手册中已经建立的用例立项、风险、工作流、评测、发布、健康、运行与移交资产，应用到两个代表性用例：**产品周会纪要与待办提取**（`UC-PROD-001`）和**高频客户咨询回复草拟**（`UC-CS-001`）。

> **证据边界**：本目录已填写的是用例范围、控制设计、验证步骤、责任分工、通过/停止条件和证据索引；其中任何需要真实业务样本、系统日志、人工审核记录、成本、耗时、采用率、客户影响或演练结果的字段，均明确标为 **【待现场验证】**。本目录不声称已执行真实生产运行、回归、发布、事件或移交，也不以设计样例替代现场证据。

| 文件 | 用途 | 现场填充者 |
| --- | --- | --- |
| `UC-PROD-001_会议纪要试点证据包.md` | 会议纪要用例的试点、验收、运行、移交与验证记录 | 产品 Owner、会议主持/记录者、Skill/流程 Owner、技术或交付支持者 |

建议将敏感原始材料放在组织内部、受访问控制的位置，并在本目录只记录脱敏的证据标识、版本、结论与链接。不要将客户信息、会议敏感信息、访问令牌、完整日志、合同、员工信息或未批准的外部材料提交到公开仓库。

## 三、现场验证的最小执行顺序

1. **确认边界**：业务 Owner 确认真实业务范围、参与者、人工备用流程、数据分类和停止条件；更新用例立项卡与风险初筛。
2. **准备样本**：由业务/知识 Owner 提供经批准、最小必要、可脱敏的真实或关闭样本；为每个样本分配内部证据编号，不把原始敏感内容写入本仓库。
3. **运行与审核**：按工作流合约执行；记录每一次任务的版本、审核结论、修改原因、转人工/回退、耗时和采用结果。
4. **评测与发布判断**：使用 Golden Set、Rubric 和回归报告比较候选与稳定版本；未达到门槛时不扩大范围。
5. **演练与移交**：至少完成一次人工备用或异常演练、一次第二人独立运行；由业务 Owner 决定是否接收、限量继续、修复或停止。
6. **证据沉淀**：将已批准结论写入健康卡、发布登记、事件记录、移交清单、组合台账与审计证据索引。

## 四、真实证据的最小字段

每条现场记录应至少包含以下信息：

| 字段 | 说明 |
| --- | --- |
| 记录编号与时间 | 能定位一次任务、一次评测、一次发布或一次演练。 |
| 用例/工作流/Skill 版本 | 避免将不同配置、知识或模型结果混在一起。 |
| 样本或任务类别 | 可使用脱敏类别、哈希或内部受控链接，不必存原文。 |
| 人工审核与采用结论 | 通过、需修改、转人工、回退、未采用及理由。 |
| 质量/风险信号 | 关键字段遗漏、知识时效、格式、越权、成本、权限或接管情况。 |
| 证据位置与 Owner | 指向受控存储位置；记录谁对其完整性负责。 |

## 五、严禁将下列项目当作证据

- 只展示一次效果良好的 Demo，或只保留成功样本。
- 仅使用公开基准、通用提示词或供应商宣传作为业务可用性结论。
- 将“模型有某项功能”代替真实工作流、数据、权限和人工审核验证。
- 用登录次数、调用量或 Token 消耗代替业务采用、质量或风险控制证据。
- 将未经授权的客户、会议、员工或合同信息写入公开 Markdown、评测集或案例库。

## 六、完成条件

两个用例在现场验证后，只有同时满足以下条件，才可从“待现场验证”改为“附条件接收”或“接收”：业务 Owner 确认范围与价值；质量/回归证据达到预先同意的门槛；风险、知识、权限、人工确认和回退控制实际可用；至少一名非设计者能够独立运行；一次人工备用或异常恢复演练完成；所有遗留问题、观察期与下一决策均已记录。
