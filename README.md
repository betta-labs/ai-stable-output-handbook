# 企业 AI 稳定产出手册（Enterprise AI Stable Output Handbook）

> 让 AI 真正落地：从最小闭环到企业运行系统，面向业务、交付、治理与培训的可复现 AI 工作方法。

**主书名**：《企业 AI 稳定产出手册》
**传播语**：让 AI 真正落地
**仓库**：betta-labs/ai-stable-output-handbook
**工作版本**：v2.0.0
**状态**：本仓库包含方法章节、模板资产、动态事实治理与待现场验证的试点证据包。公开案例只支持其来源记载的有限事实；教学情景必须明确标注为非事实演练。除非文件明确标注受控运行证据，内容应视为方法与示例，而非生产验收结论。

**v2.0.0 范围**：在可复现工作流、Skill、受控 Agent、上下文/记忆/工具治理、试点评测与运行韧性基础上，补入事实时效治理、公开案例来源边界、价值评估证据、人机协同与目标受托章节，以及 Coding Agent、Work Agent 和目标契约等可复用资产。

## 本手册解决什么问题

本手册讨论企业实践中可能反复出现的情形：个人任务的局部提效未能迁移为团队能力；演示结果在真实业务中难以复现；工具、知识、权限或责任边界不清；以及用例缺少验证、发布、运行和治理机制。

本手册的核心问题是：**在明确业务边界、人工责任和风险控制的前提下，如何让 AI 参与的工作产生可复核、可维护、可接管的结果。**

### 核心论证链：为什么先建运行系统，而不是先换模型

本手册的中心主张不是“模型越强，结果越稳定”，而是：企业 AI 的价值必须通过一个能持续运行的工作系统实现。为避免读者把它当成口号，可将本书的论证压缩为以下四步：

| 论证位置 | 本手册的判断 | 主要依据 | 如果依据不成立 |
| --- | --- | --- | --- |
| **主张** | 企业 AI 的价值在可复核、可维护、可接管的运行系统，不在单次 Demo 或模型调用量。 | 个人提效进入真实协作后会遇到输出波动、知识过期、责任不清和无法复用。 | 不把单次成功写成组织价值，回到真实任务与失败样本核对。 |
| **理由** | 稳定产出取决于任务边界、知识/上下文、人工判断、权限和回退是否彼此配合。 | 第 2、4、5、6、9、12、14、15 章的诊断、工作流、资产与治理机制。 | 先补缺失的 Owner、输入边界、审核或回退，不以换模型代替系统定位。 |
| **证据** | 每个阶段都应留下与风险相称的样本、来源/版本、验证、人审、运行和阶段决策记录。 | 用例立项卡、最小闭环、Golden Set、事实卡、运行记录、组合台账与退役记录。 | 降级为探索或教学情景；不宣称 ROI、不扩大范围、不提高自主性。 |
| **决策** | 只有当业务价值、质量/采用、知识/数据、责任、回退和运行控制证据同时满足，才扩大或提高自主性。 | 阶段闸门、指标反证、风险签字与能力移交条件。 | 修复、缩小、暂停、转人工或退役，均是正常的下一步。 |

读者可以把这张表当作全书的导航：遇到新建议时，先问它属于主张、理由、证据还是决策；如果不能回答“依据什么”和“缺什么就停止”，就不应把它直接写成上线或扩大结论。

### 更短的入口：六类焦虑与轻量启动

如果你是从“老板要求上 AI”“员工不动”“账算不清”或“Demo 进工作流就翻车”这类问题进入，可先[按六类焦虑分流](start.md)，再回到相应章节和资产。若团队人少、预算有限，只想先判断一个高频小场景是否值得继续，直接进入[轻量启动](lightweight-start.md)；它只压缩第一轮的学习与判断，不删掉 Owner、允许输入、人工审核或回退。

1. **在线阅读**：访问 [handbook.sanage.xyz](https://handbook.sanage.xyz/) 使用站内搜索、章节深链、模板导航和阅读分流；GitHub 仓库仍是版本、来源、事实卡和协作反馈的唯一真源。
2. **如果你负责组织级投入**：先阅读[企业 AI 战略与业务对齐](01-开篇-企业AI战略与业务对齐.md)，决定为什么做、做什么、明确不做什么；再阅读[高管执行摘要](executive-summary.md)，掌握阶段闸门、关键指标与风险签字责任。
3. **如果你正在判断一个团队或工作流**：从[第 2 章 自诊断](02-第2章-自诊断：定位你的真实问题.md)开始，再进入第 6 章设计最小闭环。

6. **本地阅读与维护**：克隆本仓库后，使用支持 Markdown 的编辑器阅读正文和维护资产。

### 先判断你此刻能做什么

| 层级 | 你现在可以做的事 | 进入试点前必须具备的事 | 不应由你单独决定的事 |
| --- | --- | --- | --- |
| **一个真实任务** | 写下任务、当前人工做法、不可接受的结果，以及“不用 AI 也必须完成”的原因。 | 有能定义范围并接受/拒绝结果的业务 Owner；输入允许使用；有人审核且能转回人工。 | 数据处理边界、对外承诺、关键决策、写入操作、例外接受与正式上线。 |
| **信息不足时** | 将问题登记为“待澄清”，缩小为不含敏感数据的整理/练习任务，或先纯手工完成。 | 来源、版本、权限和适用范围可说明。 | 用个人工具、猜测输入边界或以 Demo 代替审批。 |

如果无法说明 Owner、允许输入或人工接管，本手册的正确起点是**暂不启动该试点**，而不是换模型、堆资料或开始搭建 Agent。第 2 章会帮助你记录阻塞条件与正确路由。

## 文档站开发与部署

本仓库内置 VitePress 阅读站。它直接渲染本仓库 Markdown，不复制正文；页面标题、摘要与稳定路由在 `.vitepress/page-meta.ts` 中维护，站点地图、规范链接、社交分享元信息和 JSON-LD 结构化数据由 `.vitepress/config.mts` 在构建时生成。

```bash
corepack enable
pnpm install
pnpm docs:dev
```

提交前请执行：

```bash
pnpm verify
```

GitHub Actions 会在 `main` 分支的内容或站点配置更新后构建并发布到 GitHub Pages。首次启用时，需要在仓库的 Pages 设置中选择 **GitHub Actions** 作为来源，并为 `handbook.sanage.xyz` 配置指向 GitHub Pages 的 DNS CNAME。构建默认使用 `public/og-handbook.svg` 作为社交分享图；如需覆盖更多社交平台的预览兼容性，发布前可将其替换为同名 1200×630 PNG，并同步更新 `.vitepress/config.mts`。
